A concise presentation script and walkthrough guide for every published feature branch.

How to use these notes: Each branch has a short talk track, a suggested demonstration, and the test evidence or remaining limitation. Adapt the talk track to the audience; do not present provisional product rules or unverified database flows as approved or complete.

Opening: what LendLoop does

Suggested opening: "LendLoop is a campus-focused peer-to-peer lending system. Students can list items, request to borrow them, coordinate through private messaging, and track notifications, reputation, rewards, and safety reports."

The React/Vite frontend is in frontend/; the Express/Mongoose API is in backend/; MongoDB stores application data. The API owns validation, access control, and business rules. Browser authentication uses an HTTP-only cookie, and API responses follow a consistent success/error envelope.

These notes follow the published branch ancestry so each pull request can be merged after its prerequisite branch. The BE-03 routing foundation appears before BE-02 authentication in that history; the sequence is intentionally not a simple ticket-number sort.

  1. INT-01 - Initial project structure
  2. BE-01 - Database schemas
  3. BE-03 - API routing
  4. BE-02 - Authentication
  5. BE-04 through BE-11 - Backend capabilities
  6. FE-01 through FE-09 - Student-facing screens
  7. INT-02 through INT-07 - Integration and system testing
Important caveats to state clearly: Full persistence and transaction-heavy end-to-end flows still need MongoDB configured as a replica set. The five-loan cap and credit/reward rules are prototype values pending group approval. "Referred to OSA" is an internal report status, not a live OSA connection.

LL-BE-09 | Implement student credit score system

feature/LL-BE-09-credit-score

Say: "This branch makes reputation server-owned. The API records score events when loans are returned, prevents client edits, and exposes the student's current score and history."

Show: Describe the event ledger and bounds/idempotency safeguards. The current prototype values are a 100-point starting score, plus two for on-time return, and minus ten for late return.

Evidence: Score bounds and rule tests were recorded; 26 backend tests passed. These values are provisional, and return-event persistence needs MongoDB integration.

Say: "This branch adds a server-maintained reward balance and event ledger. The client can view its rewards but cannot grant itself points."

Show: Explain the idempotency key that prevents duplicate awards when the same return event is processed again. The current prototype awards 50 points for an on-time return.

Evidence: Award and protected-balance tests were recorded; 28 backend tests passed. The points rule is provisional and persistent ledger behavior needs replica-set testing.

Closing: what is ready and what remains

Suggested closing: "The project now has a structured frontend/backend foundation, API-backed student experiences, and server-side rules for lending, messaging, notifications, reputation, rewards, and reporting. The recorded automated checks pass, but we are not calling the database workflows fully accepted until we run them against a configured MongoDB replica set."

Before presenting a live demo

  1. Start the frontend and API with the documented local environment configuration.
  2. Use a disposable test database; do not present production or personal account data.
  3. For borrow/return and other transaction flows, use MongoDB configured as a replica set.
  4. Use two test accounts for owner/borrower and participant-isolation demonstrations.
  5. Present the five-loan cap and score/reward values as provisional, not approved policy.
  6. Describe OSA referral as an internal workflow status unless a real integration is separately built and approved.
